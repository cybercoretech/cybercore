Architecture and product map

Cybercore uses a shared Rust framework for themes, components, effects, packs, quality checks, and updater operations. Products consume the shared contracts while keeping their own runtime and presentation layers.

Core surfaces

SurfaceResponsibility
Core cratesTokens, components, effects, packs, and validation
Theme StudioLocal theme authoring and preview
Updater engineDiscovery, planning, installation, repair, and rollback
Updater TUIKeyboard-driven operator dashboard
Updater PanelLoopback Control Panel for fleet operations
Public docsSanitized reference published from Cybercore-owned source

The updater manifest defines product consumers and shared synchronization tasks. The public task pages are generated from that manifest so names and coverage remain aligned.

Updater operations

The compatibility command is dry-run by default:

cybercore-update
cybercore-update --apply
cybercore-update --tui

The Rust surfaces provide planning, inspection, apply, repair, service restart, rollback, theme health, GitHub read-only status, repository diff review, and bounded operation history.

Safety rules

  • Dirty worktrees are blocked unless generated outputs are explicitly allowlisted.
  • Apply, repair, restart, and rollback require explicit confirmation.
  • Binary replacement creates a backup before installation.
  • User services use systemctl --user; system escalation is never silent.
  • The updater does not commit or push repository changes automatically.

Updater Control Panel

The loopback Control Panel exposes the fleet dashboard and extended operations without replacing the CLI or TUI.

Supported operations

  • Fleet task discovery and diagnostics
  • Non-mutating plan generation
  • Apply, repair/retry, service restart, and rollback actions
  • Visible action results and duplicate-action protection
  • Theme and repository workspace status

The Panel is intended for local use. Keep it bound to loopback and place any remote access behind an authenticated, explicitly configured gateway.

Themes and assets

Cybercore’s target theme model contains 312 themes:

  • 300 canonical source palettes
  • 12 signature mashups

Theme synchronization derives from the canonical public registry, preserves family metadata, and tracks generated outputs so unrelated local themes are not removed.

Theme quality checks cover schema validity, rendering, contrast, appearance variants, and shared component compatibility. Theme Studio is the authoring surface; products consume the resulting public contracts.

Recovery and validation

Before release, validate the Rust workspace, compatibility dry-run, updater plan, live fleet diagnostics, services, and theme totals.

Recovery

The updater creates a sibling backup before replacing an installed binary. Rollback restores the most recent backup for a selected task. Repair retries a blocked or failed task after its diagnostic condition has been resolved.

Troubleshooting

  1. Run a dry-run and inspect the first blocked diagnostic.
  2. Resolve missing sources, dependency, or dirty-worktree conditions.
  3. Re-run the plan before applying.
  4. Apply only after the plan is clear.
  5. Record the result in the operation history.
